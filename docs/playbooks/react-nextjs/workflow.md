# Workflow

React / Next.js 制作案件で、Codex と一緒に作業するときの共通ルールです。

このファイルは全案件に共通する親ルールとして扱い、案件固有のURL、会社名、サーバー構成、公開手順、DB仕様は各プロジェクト側のmdに残します。

## 親ルールと案件ルールの分け方

- 共通ルールはこのプレイブックに集約する
- 各案件の `AGENTS.md` には、このプレイブックへの参照と案件固有の注意点を残す
- 他案件からmdを流用して良かったルールは、案件内だけで育てず、このプレイブックにも反映する
- どのmdが最新か迷う場合は、このプレイブックを先に確認する
- 案件側のmdは、親ルールとの差分とその案件だけの地雷を記録する

## バージョン確認

- 新規案件は、その時点の Next.js Active LTS を基準にする
- 既存案件では `package.json` と lockfile を確認し、実際のバージョンを優先する
- 「Next.jsでは常にこうなる」と固定せず、バージョン依存の仕様は対象バージョンの公式ドキュメントで確認する
- Next.js 15以前のルールを、確認せずNext.js 16以降へ流用しない
- Next.js 16では `params` や `searchParams` などのRequest APIを非同期で扱う
- Next.js 16では `next lint` を使わず、ESLint CLIまたは採用したLintツールを直接実行する
- 静的書き出し案件は `nextjs-static-export.md` も確認する

## パス記載ルール

- レビュー結果、作業ログ、仕様書、外部レビュー依頼書など、共有される可能性があるmdにはマシンの絶対パスを記載しない
- 対象プロジェクトは案件名または「プロジェクトルート」と記載する
- ファイルやディレクトリは、プロジェクトルートを基準にした相対パスで記載する
- macOSのユーザー名やローカルのディレクトリ構成が分かる `/Users/...` などのパスを成果物へ残さない
- ローカルでのファイル操作や環境設定に絶対パスが必要な場合のみ使用し、共有用mdやレビュー結果には転記しない

記載例:

```md
対象プロジェクト: 雄建サイト
対象ディレクトリ: プロジェクトルート
対象ファイル: `src/app/layout.tsx`
```

## HTML / TSX生成ルール

- 公開側で表形式のレイアウトを新規作成する場合は、原則としてtableタグを使わず、`div` または `ul` と CSS Grid で構成する
- 表としての意味を読み上げにも伝える必要がある場合は、必要なARIAロールを適切に付与する
- 既存のtableタグは、明確な依頼がない限り一括変更しない
- 詳細な採用条件と例外は `patterns.md` の「tableタグを使わない表形式レイアウト」を参照する

## レビュー運用ルール

レビュー関連のルールは、通常レビュー・公開前チェック・外部レビュー依頼・外部レビュー後の対応をまとめてこの項目で管理します。

詳細な確認観点、保存ルール、外部レビュー依頼と修正トラッカーのテンプレートは `review.md` を参照します。

管理画面 / DB連携、SEO、公開手順とは役割が違うため、レビュー運用は混ぜずに分けて残します。

### レビュー作業ルーティン

プログラムチェック、公開前チェック、Claudeなどの外部レビュー後の対応では、`docs/review/REVIEW_YYYY-MM-DD.md` を作成または更新します。

外部レビュー依頼時は `docs/review/REVIEW_REQUEST_TEMPLATE.md` を元に、`docs/review/REVIEW_REQUEST_YYYY-MM-DD.md` を作成します。

外部レビュー指摘の対応状況は `docs/review/REVIEW_FIX_TRACKER_TEMPLATE.md` を元に、`docs/review/REVIEW_FIX_TRACKER_YYYY-MM-DD.md` で管理します。

レビューmdの冒頭には `進捗サマリー` を置き、作業状況を一覧できるようにします。

| 状態          | 意味                                           |
| ------------- | ---------------------------------------------- |
| ✅ 対応済み   | 実装または判断が完了している                   |
| ⏳ 再確認待ち | ユーザー確認、公開後確認、ビルド確認などが必要 |
| ⚠️ 要確認     | 仕様判断や外部状況の確認が必要                 |
| ⬜ 未対応     | まだ作業していない                             |

各項目には、対象ファイル、対応内容、確認方法、残タスクを残します。

レビュー指摘を修正し、必要な確認とユーザー確認が完了したら、次の項目へ進む前に対象レビューmdの進捗サマリーと該当項目を `✅ 対応済み` へ更新します。

### 外部レビュー指摘への対応方針

Claudeなど外部レビューの指摘は、まず既存仕様、公開運用、管理画面やDB連携方針と矛盾しないか確認します。

矛盾しない範囲では、Codex側の判断で最小修正してよいものとします。

ただし、以下に該当する場合は、修正前にユーザーへ確認します。

- ページ構成や導線が変わる
- 見た目の印象が大きく変わる
- class名・id属性・データ構造・JSON項目など、既存実装や管理画面連携に影響する可能性が高い
- 仕様mdと実装のどちらを正とするか判断が必要
- JavaScriptの処理追加・削除など、挙動が変わる
- 複数ファイルにまたがる大きめの変更になる
- 指摘内容が「好み」か「実装上の問題」か判断しづらい

対応した項目は、日付別レビューmdの進捗サマリーにも反映します。

### 外部レビュー結果の保存

- Claudeなどの外部AIへレビューを依頼する場合は、結果をチャットだけで返さず、外部AI自身が `docs/review/EXTERNAL_REVIEW_ツール名_YYYY-MM-DD.md` に保存する
- Claudeの場合は `docs/review/EXTERNAL_REVIEW_CLAUDE_YYYY-MM-DD.md` とする
- 外部レビューの原文は加工せず保存し、Codex側の判断や対応記録とは分けて管理する
- 同じ日付のファイルが存在する場合は上書きせず、`_02`、`_03` のように連番を付ける
- 外部レビュー依頼用のプロンプトには、最初にプロジェクトの `AGENTS.md` を確認するよう明記する
- 指摘への対応状況は `docs/review/REVIEW_FIX_TRACKER_YYYY-MM-DD.md`、実際の修正内容・確認方法・残タスクは `docs/review/REVIEW_YYYY-MM-DD.md` に記録する

案件側には、必要に応じて次のテンプレートを用意します。

- `docs/review/REVIEW_REQUEST_TEMPLATE.md`
- `docs/review/REVIEW_FIX_TRACKER_TEMPLATE.md`

テンプレートの共通原本は `review.md` に置き、案件側では技術構成、公開方式、対象範囲など案件固有の項目だけを調整します。

## ビルド運用

- 基本作業中はユーザー側で `npm run dev` を起動し、ブラウザ表示を確認している前提で進める
- Codex側では `npm run build` / `npm run build:demo` / `npm run build:prod` を実行しない
- ビルド確認が必要な場合は、Codex側で実行せず「ここでビルド確認をお願いします」とユーザーに伝える
- Codex側で行う確認は、必要に応じて `npx tsc --noEmit` や対象ファイルの `prettier --check` など、ビルドを伴わない範囲に留める

### デモ・本番用scripts

デモ環境と本番環境でmetadata、robots、sitemapなどを切り替える案件では、`cross-env`を`devDependencies`へ追加し、次の形を基本とします。

```json
{
  "scripts": {
    "build:demo": "cross-env NEXT_PUBLIC_IS_REAL_PROD=false NEXT_PUBLIC_METADATA_BASE=https://demo.example.com/ next build",
    "build:prod": "cross-env NEXT_PUBLIC_IS_REAL_PROD=true NEXT_PUBLIC_METADATA_BASE=https://example.com/ next build"
  }
}
```

- URLは例示をコピーせず、各案件のデモURLと正式な公開URLへ置き換える
- `NEXT_PUBLIC_IS_REAL_PROD`は文字列として渡されるため、コード側では `=== 'true'` で判定する
- `NEXT_PUBLIC_METADATA_BASE`はmetadata、canonical、OGP、robots、sitemapで使用する基準URLと連動させる
- `NEXT_PUBLIC_`が付く環境変数へ秘密情報を入れない
- 環境変数名と切り替えの仕組みは共通ルール、実際のURLと公開手順は案件側のmdへ記録する
- `output: 'export'` の案件では `next start`を通常の確認・公開手順に含めず、書き出した静的ファイルを対象環境の方法で配信する

## 作業ログ

- 実装した内容は、必要に応じて日付別レビューmdまたは `docs/MEMORY.md` に残す
- ユーザーがあとから見ても「何を直したか」「何が残っているか」「どこを確認すればよいか」が分かる形を優先する
- 大きな判断、保留、公開後確認が必要な項目は必ず記録する
