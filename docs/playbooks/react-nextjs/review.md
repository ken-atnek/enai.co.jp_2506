# Review

React / Next.js 制作案件で、通常レビュー、公開前チェック、外部AIレビューを同じ形式で管理するための共通仕様です。

案件固有のURL、公開手順、DB仕様などは、このファイルへ追加せず各案件の `AGENTS.md` や `docs/` に残します。

## 基本方針

- レビュー結果はチャットだけで終わらせず、案件側の `docs/review/` に保存する
- 指摘は一般論ではなく、対象ファイルと行番号、実際の影響、確認方法を示す
- 既存仕様、既存デザイン、公開運用、管理画面やDB連携方針との整合を先に確認する
- 大幅な作り直しではなく、問題を解消できる最小修正を優先する
- コードだけで断定できない表示崩れは、推測で直さず実機またはDevToolsで確認する
- 未使用コードや命名差だけを理由に、依頼範囲外の削除やリネームを行わない
- 外部レビューの原文と、Codex側の判断・対応記録を分けて管理する

## 保存ファイル

| 目的 | ファイル名 |
| --- | --- |
| 日付別のレビューと実装記録 | `docs/review/REVIEW_YYYY-MM-DD.md` |
| 外部AIへのレビュー依頼 | `docs/review/REVIEW_REQUEST_YYYY-MM-DD.md` |
| 外部AIのレビュー原文 | `docs/review/EXTERNAL_REVIEW_ツール名_YYYY-MM-DD.md` |
| 外部指摘の対応状況 | `docs/review/REVIEW_FIX_TRACKER_YYYY-MM-DD.md` |

同じ日付・同じ種類のファイルが存在する場合は上書きせず、ファイル名の末尾に `_02`、`_03` のような連番を付けます。

共有用mdにはマシンの絶対パスを記載せず、プロジェクトルートを基準にした相対パスを使用します。

## ステータス

| 状態 | 意味 |
| --- | --- |
| ✅ 対応済み | 実装または判断が完了している |
| ⏳ 再確認待ち | ユーザー確認、実機確認、公開後確認などが必要 |
| ⚠️ 要確認 | 仕様判断や外部状況の確認が必要 |
| ⬜ 未対応 | まだ作業していない |
| 対応不要 | 実装と照合し、変更しないと判断した |

## レビューの進め方

1. 案件側の `AGENTS.md` と関連仕様mdを確認する
2. 対象範囲と、実行してよい確認コマンドを確認する
3. 実装と仕様を照合し、指摘に優先度を付ける
4. 外部レビューの場合は原文を加工せず保存する
5. 指摘を実装と再照合し、修正、要確認、対応不要に分類する
6. 仕様確認が不要な項目だけを最小修正する
7. 静的チェックと表示確認を分けて実施する
8. 日付別レビューmdと修正トラッカーへ結果と残タスクを反映する

## 修正前にユーザー確認が必要な項目

- ページ構成や導線が変わる
- 見た目の印象が大きく変わる
- class名、id属性、データ構造、JSON項目など既存連携への影響が大きい
- 仕様mdと実装のどちらを正とするか判断が必要
- JavaScriptの追加や削除により挙動が変わる
- 複数ファイルにまたがる大きめの変更になる
- 指摘が好みの問題か、実装上の問題か判断しづらい

## 共通の確認観点

### 実装・表示

- HTML / JSX構造と見出し階層
- SCSS、ブレークポイント、スマートフォン横向き、タブレット縦向き
- モーダル、メニュー、フォームなどのキーボード操作とフォーカス制御
- 画像パス、画像の実在、alt、OGP画像
- ローディング、取得失敗、空データ時の表示
- イベントリスナーや副作用のクリーンアップ

### Next.js / 静的書き出し

- `output: 'export'` と矛盾する実装がないか
- 動的ルートがビルド後のデータ増減を前提にしていないか
- `public/db` などの更新データをクライアント取得する方針と一致しているか
- デモと本番で、環境変数や公開パスの切り替えが意図どおりか
- ビルド成果物から除外するファイルと、公開サーバーに残すファイルが明確か

### SEO・公開

- metadata、canonical、OGP、Twitter Card
- sitemap、robots、noindexの本番・デモ切り替え
- 旧URL、www有無、HTTPからHTTPSへのリダイレクト
- 問い合わせフォームの送信先と本番受信確認
- 公開サーバー上でのみ確認できる項目が残タスク化されているか

### 保守・安全性

- 型、Lint、Format、Stylelintなどビルドを伴わない静的チェック
- 秘密情報や個人情報がコード、コメント、成果物に残っていないか
- mdと実装、型とJSON、参照先ファイルの整合
- 指摘が実害のある問題か、提案レベルかを区別できているか

## 外部レビュー依頼テンプレート

案件側の `docs/review/REVIEW_REQUEST_TEMPLATE.md` にコピーし、案件固有の前提と確認範囲だけ調整します。

```md
# 外部レビュー依頼

最初に、このプロジェクトの `AGENTS.md` と関連する仕様mdを確認してください。

## 依頼内容

実装済みのコードとmdを照合し、公開前レビューをしてください。

## 前提

- 技術スタック:
- 公開方式:
- データ取得方式:
- 既存構成を優先し、大幅リファクタは前提にしない

## 確認対象

- 対象ページ:
- 対象ディレクトリ:
- 対象外:

## 優先して確認する観点

1. 画面が壊れる、実行できない問題
2. 公開後のSEOやインデックス制御に関わる問題
3. データ更新や外部連携が反映されない問題
4. スマートフォン、タブレット、PCでの表示崩れ
5. アクセシビリティと操作不能につながる問題
6. mdと実装の矛盾

## 指摘ごとの必須項目

- ID
- 重要度: 致命的 / 高 / 中 / 低
- 対象ファイルと行番号
- 問題の内容
- 実際の影響
- 再現条件または確認方法
- 最小修正案
- 仕様確認の要否

## 出力構成

1. 進捗サマリー
2. 致命的な問題
3. 優先度「高」の問題
4. 優先度「中」の問題
5. 優先度「低」の問題
6. mdと実装の矛盾
7. SEO・公開設定の懸念
8. 確認したが問題がなかった主要項目
9. 要確認事項
10. 公開前に行う確認手順
11. 総評
12. 指摘一覧表

## 保存ルール

- 結果はチャットだけで返さず、外部AI自身が `docs/review/EXTERNAL_REVIEW_ツール名_YYYY-MM-DD.md` に保存する
- 原文は要約や加工をせず保存する
- 同名ファイルがある場合は上書きせず `_02`、`_03` のように連番を付ける
- ファイルはプロジェクトルート基準の相対パスで記載し、マシンの絶対パスは残さない

## 注意

- 一般論ではなく、このプロジェクトの実装を根拠に指摘する
- コードだけで断定できない表示上の懸念は「要確認」とする
- 未使用や命名差だけを理由に、削除や大規模変更を前提にしない
- 問題が見つからなかった確認項目も記録する
```

## 日付別レビューmdに残す内容

日付別レビューmdの冒頭には進捗サマリーを置きます。各項目には次を残します。

- ステータス
- 対象ファイル
- 指摘または確認内容
- 対応内容と判断理由
- 確認方法と結果
- 残タスク

静的チェックで確認済みの内容と、ユーザー側のビルド、実機、本番サーバーで再確認する内容は混ぜずに記載します。
