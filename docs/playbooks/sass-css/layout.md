## レイアウトの責務を分ける

### 使う場面

セクション、コンポーネント、カード、テキストブロックなどが混ざり、余白や幅指定が複雑になっている画面。

### 実装方針

- 外側のセクションは背景、上下余白、表示領域を担当する
- 内側のコンテナは最大幅と左右余白を担当する
- コンポーネント自身は中身の配置と最小限の余白を担当する
- 同じ余白を複数階層で重ねない

### 判断基準

- その指定が「ページ全体の都合」か「部品単体の都合」かを分ける
- 別ページに持っていっても成立する指定だけをコンポーネント側に置く
- 背景の塗り分けとコンテンツ幅の指定を混ぜない

### 避けること

- 子要素側の `margin` でセクション全体の余白を作る
- コンポーネント内にページ固有の最大幅を持たせる
- 見た目合わせのために親子両方へ似た `padding` を入れる

## 配置は Flex と Grid の役割で選ぶ

### 使う場面

横並び、カード一覧、フォーム、メディアレイアウトなど、並べ方を決める場面。

### 実装方針

- 1方向の整列は Flex を基本にする
- 行と列の両方を制御する一覧や面の構成は Grid を検討する
- 中身の量で自然に折り返したい場合は Grid の `auto-fit` / `minmax()` を検討する
- 余白は `gap` を優先し、隣接要素の `margin` 依存を減らす

### 判断基準

- 並び順が1列または1行の流れなら Flex
- カラム幅や行揃えが重要なら Grid
- SP/PCで列数が変わるなら Grid の方が管理しやすいことが多い

### 避けること

- 2次元レイアウトを Flex の幅指定だけで無理に組む
- 一覧の余白を `:nth-child` や個別 `margin` で管理する
- 目的が中央寄せだけなのに過剰なラッパーを増やす

## 絶対配置は役割を限定する

### 使う場面

バッジ、装飾、重ねるアイコン、画像上のラベルなど、通常の文書フローから外したい要素。

### 実装方針

- 基準になる親要素を明確にする
- 通常フローで置ける要素は通常フローに残す
- テキスト量や画面幅で重なりやすい要素には使わない
- `z-index` は必要な局所だけで管理する

### 判断基準

- その要素が本文レイアウトに影響しなくても問題ないか
- 可変テキスト、画像比率、改行で破綻しないか
- SP表示でも同じ重ね方が成立するか

### 避けること

- レイアウト調整の主手段として `position: absolute` を使う
- テキストやボタンを安易に重ねる
- `z-index` の値を場当たり的に大きくする

## sibling-count() で要素数に応じた配置を作る

### 使う場面

カード、アイコン、装飾パーツ、手札風UI、円形配置など、兄弟要素の数によって角度・位置・色・幅を変えたい場面。

### 実装方針

- 要素数が可変で、CSSだけで並びや角度を調整したい場合に検討する
- `sibling-index()` で現在位置、`sibling-count()` で総数を使う
- 中央基準で配置したい場合は `(sibling-count() + 1) / 2` を基準値にする
- 実務では装飾的な配置や限定UIに留め、主要レイアウトはFlex / Gridを優先する

```scss
.cards__item {
  transform:
    translateX(-50%)
    rotate(calc((sibling-index() - (sibling-count() + 1) / 2) * 8deg))
    translateY(-24px);
}
```

### 判断基準

- 要素数の増減で見た目のバランスを自動調整したいなら採用候補
- 通常の一覧・カードグリッドならFlex / Gridで十分か先に確認する
- ブラウザ対応が要件に合わない場合は、Sassループ、`nth-child()`、HTML側のCSS変数付与で代替する

### 避けること

- 本文や重要情報の読み順に関わるレイアウトを複雑な計算で組む
- 対応ブラウザが狭いのに、代替なしで主要導線に使う
- Sassで事前計算できる固定数UIまで無理にCSS関数で動的化する
